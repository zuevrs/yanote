# Project Knowledge

Append-only register of project-specific rules, patterns, and lessons learned.
Agents read this before every unit. Add entries when you discover something worth remembering.

## Rules

| # | Scope | Rule | Why | Added |
|---|-------|------|-----|-------|
| 1 | release truth | Treat signed `vMAJOR.MINOR.PATCH` tags and GitHub Releases as the public version truth, not workspace snapshot markers such as `0.0.0` or `0.1.0-SNAPSHOT`. | `docs/release-and-support.md` is explicit that workspace version markers are technical build markers, not release truth. | 2026-03-22 |
| 2 | report surfaces | Keep HTTP/OpenAPI reporting and the current async/Kafka reporting on separate public surfaces (`yanote-report.json` vs `yanote-async-report.json`) unless a future milestone explicitly proves a combined contract. | The current public boundary is intentionally split and documented that way. | 2026-03-22 |
| 3 | gsd storage | Follow the `gsd-2` shared-project model: commit durable `.gsd` docs and milestone artifacts, but keep `.gsd/runtime/`, `.gsd/activity/`, `.gsd/worktrees/`, lock/state files, and other session data local-only. | This repo previously blanket-ignored `.gsd/`, which prevents durable project memory from surviving machines and sessions. | 2026-03-22 |
| 4 | payload-format policy | Detect unsupported HTTP payload `format` keywords before Ajv compilation and register only the allowlisted formats explicitly. | With `strict: false`, Ajv will ignore unknown formats rather than fail closed, so Yanote must walk the schema first to surface honest unsupported-format diagnostics instead of silently treating formatted strings as plain `type` checks. | 2026-03-25 |
| 5 | payload-media specificity | Keep declared media extraction/report ordering lexicographically stable, but rank competing matches by specificity at evaluation time (`exact` > structured-suffix wildcard > broader wildcard). | The sorted declaration list is part of the stable report surface, while payload conformance truth must still choose `application/problem+json` over `application/*+json` when both are declared. | 2026-03-25 |

## Patterns

| # | Pattern | Where | Notes |
|---|---------|-------|-------|
| 1 | Recorder writes portable evidence, analyzer computes contract coverage | `README.md`, `yanote-recorder-spring-mvc`, `yanote-js` | The product boundary is recorder → `events.jsonl` → analyzer/report, not ad hoc runtime introspection. |
| 2 | Traceability is explicit and file-backed | `docs/requirements.md`, `docs/traceability/v1-requirements-tests.md` | Requirements, test references, and verification commands are already documented as first-class repo artifacts. |
| 3 | Public retained proof bundles ship an artifact manifest plus source-path notes beside the copied artifacts | `.yanote-ci/v1-e2e/artifact-manifest.txt`, `.yanote-ci/v1-e2e/artifact-source-paths.txt`, `scripts/ci/run-v1-e2e.sh` | When a bundle widens additively, these two files localize drift quickly: you can see whether a missing/changed artifact came from live capture, filtered replay, or host-side analyzer reruns without reverse-engineering the bundle contents. |
| 4 | Fixture-backed broader-object proofs should publish derived sidecars plus provenance, not raw fixture evidence | `.yanote-ci/v1-e2e/security-semantics.*`, `scripts/ci/run-v1-e2e.sh`, `docs/guides/analyzer-coverage.md` | When a broader OpenAPI family is proven on focused fixtures instead of the live example service, keep the public bundle to derived stdout/stderr/report artifacts plus manifest/source-path notes; do not copy the raw fixture JSONL, or docs/startup surfaces will overstate live coverage and risk redistributing fake secret-like values. |
| 5 | Broader HTTP/OpenAPI semantics should land on additive top-level conformance surfaces, not by rewriting legacy coverage numerators | `yanote-js/src/coverage/httpSecurityConformance.ts`, `yanote-js/src/report/report.ts`, `yanote-js/src/cli.ts` | When Yanote widens semantic depth, preserve canonical operation identity and stable `coverage.operations/status/parameters/aggregate` meaning; publish the new truth through a dedicated conformance/report/summary section instead. |
| 6 | Keep source-spec metadata sparse, but materialize deterministic booleans on canonical coverage/report rows | `yanote-js/src/spec/openapi.ts`, `yanote-js/src/coverage/coverage.ts` | For additive HTTP metadata like OpenAPI operation deprecation, storing only explicit `true` in `HttpOperationContract` avoids churning unrelated inline fixtures, while `coverage.perOperation` should still publish a concrete `false`/`true` value so downstream report and CLI code never has to re-derive defaults. |
| 7 | Focused retained proof bundles should pin their exact file layout and restate the high-signal claims in `artifact-manifest.txt` | `.yanote-ci/deprecated-operations-proof/`, `scripts/ci/verify-m013-s02-deprecated-operations.sh` | For narrow CLI/report proofs, keep the retained bundle HTTP-only and encode the rerun command plus assertions like `legacy_operations=2/3` and `deprecated_*` directly in the manifest so future agents can verify drift quickly without rereading the verifier script. |
| 8 | Delivery manifests and GitHub step summaries should derive `specSource`, deprecated counts, and explicit JSON/HTML artifact truth from canonical report JSON plus collected artifact directories | `scripts/ci/collect-yanote-artifacts.sh`, `scripts/ci/export-async-proof-artifacts.sh`, `scripts/ci/render-yanote-summary.mjs` | When delivery surfaces widen, using the canonical report as the metadata source keeps retained bundles, summaries, and docs aligned while avoiding hand-maintained wording drift or secret-unsafe provenance reformatting. |
| 9 | After changing live-bundle export metadata, rerun the authoritative proof before validating collected artifact manifests | `scripts/ci/verify-m004-s03-live-kafka-proof.sh`, `.yanote-ci/live-kafka-proof/`, `scripts/ci/collect-yanote-artifacts.sh` | `collect-yanote-artifacts.sh` faithfully republishes the already-exported live bundle; it will not backfill newly added manifest/source-path fields into a stale `.yanote-ci/live-kafka-proof/` from an earlier run. Regenerate the live bundle first, then re-collect and re-render summaries. |

## Lessons Learned

| # | What Happened | Root Cause | Fix | Scope |
|---|--------------|------------|-----|-------|
| 1 | Blanket-ignoring `.gsd/` leaves GSD planning memory entirely local and easy to lose. | The repo treated `.gsd` as an all-local cache instead of separating durable docs from runtime residue. | Use the `gsd-2` shared-project ignore model: commit durable `.gsd` docs, ignore only runtime/state/worktrees. | `.gsd/` maintenance |
| 2 | Spring MVC URI template variables are only reliable after handler mapping has run. | `HandlerMapping.URI_TEMPLATE_VARIABLES_ATTRIBUTE` is populated by Spring MVC during request handling, not on the raw incoming servlet request. | Capture path-parameter evidence when recording after `filterChain.doFilter(...)`, even if other request surfaces could be read earlier. | Spring MVC recorder evidence |
| 3 | `npm -C yanote-js ci` and `npm --prefix yanote-js ci` can report success in this worktree without creating `yanote-js/node_modules` or a local `vitest` bin. | The install command completed normally, but `yanote-js/node_modules/.bin/vitest` still did not exist and `npm -C yanote-js test ...` continued to fail with `vitest: command not found`. | Verify the local bin path after install before trusting Node test readiness in `.gsd/worktrees/M011`; treat a missing bin as a worktree tooling issue, not necessarily a code failure. | M011 worktree Node verification |
| 4 | `vitest run` with a mixed list of existing and not-yet-created file arguments still exits 0 and only runs the files that exist. | The slice-level `npm -C yanote-js test -- ... report.requestEvidence ... cli.requestEvidence ...` command passed at T02 even though the T03-specific test files were not in the tree yet. | Do not treat the slice-level Vitest file list as proof that every later-task surface exists; verify missing-file surfaces with the shell proof or explicit `find`/`read` checks when task ownership matters. | M011 request-evidence verification |
| 5 | CLI request-conformance issue text can leak raw observed values if it reuses analyzer `diagnostic.reason` strings verbatim. | `captured-invalid` and repeated-value `unsupported` reasons embed the retained scalar values, which is fine for report JSON artifacts but too leaky for stdout summaries. | In `yanote-js/src/cli.ts`, render request-conformance Top Issues from `diagnostic.message` plus `evidenceReason` only; keep raw `observedValues` on the JSON report surface instead of the CLI. | M011 request-evidence reporting |
| 6 | Focused OpenAPI proof bundles can turn `yanote report` status `partial` if service readiness checks hit undeclared HTTP routes first. | The recorder captures every live HTTP request, so using `/health` as a readiness probe injected unmatched evidence into the focused request-evidence bundle even though the proof route itself was correct. | For focused verifier scripts and isolated RestAssured proofs, wait on the TCP port instead of making recorded HTTP readiness calls unless the readiness route is declared in the proof spec. | M011 focused live-proof verification |
| 7 | Exact Gradle `--tests` slice verifiers can miss package-private JUnit 5 classes even when the test class exists and compiles. | Gradle test filtering by fully qualified class name in this repo did not discover package-private focused test classes, causing false `No tests found for given includes` failures on the slice verifier command. | Make focused JUnit classes public when they are targeted directly by exact `--tests` filters, then rerun the exact verifier command instead of weakening the filter. | M011 focused Java verification |
| 8 | During M011 S02, the request support boundary is published additively before enforcement switches over. | The slice intentionally widens `requestParameters` with declared serialization support (`declaredSupport*`) while the existing first-scalar evaluator still reads the legacy `scalar*` view until later tasks teach honest array validation and fail-closed gating. | When touching request-conformance/report code in S02, preserve both surfaces: `declaredSupport*` is the public serialization matrix, while `scalar*` remains the temporary legacy evaluator input until the follow-up tasks land. | M011 request-serialization transition |
| 9 | Once request-conformance diagnostics are fed into `evaluateGateFailures`, legacy request-summary CLI tests that expected exit code `0` flip to exit code `5` before Top Issues / summary text are updated. | The governance layer now treats `captured-invalid`, `redacted`/`omitted`, and `unsupported` request truths as fail-closed semantic errors, but the pre-T04 CLI contract tests still assert the earlier medium-only request diagnostics path. | For S02 follow-up CLI work, update request-focused CLI assertions together with summary/dedupe behavior instead of treating the new exit-5 result as a regression in the evaluator wiring. | M011 request-semantic CLI boundary |
| 10 | A shell verifier that wraps a fail-closed command with `if ! command; then exit_code=$?; fi` captures the negated wrapper status instead of the command's real exit code. | In Bash, `!` flips the command result before the `then` block runs, so `$?` inside the block is no longer the underlying analyzer exit code you meant to assert. | When verifier scripts need to inspect an expected non-zero analyzer exit, capture it with an explicit `if command; then exit_code=0; else exit_code=$?; fi` (or equivalent) before making assertions. | M011 request-semantics verifier scripting |
| 11 | The shared S03 `application/problem+json` media-specificity fixture is intentionally red on the request side. | Once media matching prefers the most-specific declaration, the `/incidents` request is validated against the stricter `application/problem+json` schema, and the fixture body only has `title` while that schema also requires `detail`. | Treat this fixture as proof that specificity ranking is real; the request should fail with `INVALID_BODY` while the response stays `VALID`, not all-green. | M011 format/media specificity fixtures |
| 12 | In this repo’s GSD worktree flow, `async_bash` verification commands can resolve against the parent repo root instead of the active `.gsd/worktrees/...` checkout. | The background runner executed `npm -C yanote-js ...` under `/Users/zuevrs/Projects/yanote` while the task’s authoritative files lived under `/Users/zuevrs/Projects/yanote/.gsd/worktrees/M011`, which made relative verifier paths disagree even though the worktree script itself was valid. | For authoritative auto-mode verification in a worktree, prefer `bash` (or explicitly verify the cwd) before trusting a failing `async_bash` result. | M011 worktree verification |
| 13 | Bash exact-string verifier needles that include Markdown backticks can fail before `grep` ever runs if they are wrapped in double quotes. | In shell, backticks inside double-quoted strings trigger command substitution, so a verifier like `require_contains ... "`email`-only ..."` explodes with `command not found` or EOF errors instead of checking the doc text. | In repo verifier scripts, wrap exact-string needles containing backticks in single quotes (or escape the backticks) before passing them to `grep -F`. | M011 doc verifier scripting |
| 14 | Exact fully qualified Gradle `--tests` filters can still miss focused JUnit classes in this repo even after the classes are made `public`, while wildcard class-name filters succeed reliably. | At M011 closeout, `./gradlew :yanote-core:test --tests 'dev.yanote.core.events.HttpEventRequestEvidenceJsonlRoundTripTest'` and the matching recorder command both returned `No tests found for given includes`, but the wildcard forms `--tests '*HttpEventRequestEvidenceJsonlRoundTripTest'` and `--tests '*HttpRequestEvidenceCaptureTest'` passed immediately on the same sources. | When a closeout proof depends on targeted Gradle test filters here, prefer wildcard class-name filters or revalidate the exact FQCN form before citing it as authoritative evidence. | M011 closeout Java verification |
| 15 | Historical focused shell proofs can drift when later slices reuse the same example route and shared integration test for a broader semantics scenario. | `scripts/ci/verify-m011-s01-request-evidence.sh` still asserted the earlier `oversizedHint` omission scenario, but the shared `HttpRequestEvidenceE2eTest` now drives the S02 `tags/meta` request-semantics path, so the legacy S01 shell proof failed even though the integrated M011 proof stack passed. | For milestone closeout, trust the latest integrated proof stack, and when a slice needs a durable historical proof command, keep it isolated from later shared-route/test evolution. | M011 verifier maintenance |
| 16 | New semantic failure codes can silently lose their intended precedence in `yanote-report.json` even when gate selection is already correct. | `buildReport()` preserves gate precedence with `sortFailuresByPrecedence`, but `normalizeReport()` re-sorts `governance.diagnostics` with its own `governanceSemanticCodeRank()` table, so newly added semantic codes fall back to the default rank unless that table is updated too. | Whenever a slice adds typed semantic failures, update both the gate precedence model and `yanote-js/src/report/normalize.ts`'s semantic rank table so normalized report JSON stays aligned with primary-failure ordering. | M012 report normalization |
| 17 | `render-yanote-summary.mjs` can show a different order for HTTP governance failures than the CLI when report diagnostics omit `operationKey`. | The GitHub-summary renderer takes the first governance error as the primary failure, but its `Top Issues` path re-sorts same-code governance entries by generated text when `operationKey` is absent, so fixture expectations can drift even though both surfaces remain deterministic. | When adding HTTP governance-summary fixtures, set the primary failure by ordering `report.governance.diagnostics` intentionally and expect `Top Issues` ordering to follow the renderer’s secondary sort (`severity/category/sortKey/text`) unless `operationKey` is present. | M012 CI summary security fixtures |
| 18 | Localhost HTTP fixture fetches can fail with proxy-style `502` responses in this repo’s agent environment even when the in-process test server is healthy. | The shell environment sets `NODE_USE_ENV_PROXY=1` plus `HTTP_PROXY`/`HTTPS_PROXY`, and Node v25 routes plain `fetch()` / default-agent `http.request()` traffic through that proxy unless the request opts out explicitly. | For localhost-backed verifier fixtures in `yanote-js`, disable the default agent (`agent: false`) or otherwise bypass env proxies before blaming the fixture server or the spec resolver. | M013 remote-spec resolver |
| 19 | Local-directory spec proofs only resolve if the retained fixture filename starts with `openapi` or `asyncapi`. | `yanote-js/src/spec/discover.ts` intentionally discovers directory specs by filename pattern (`^openapi...` / `^asyncapi...`) instead of parsing arbitrary filenames like `simple.yaml`. | When building directory-backed proof fixtures or retained bundles, name the file `openapi.yaml`/`asyncapi.yaml` inside the directory or the analyzer will fail with `INPUT_SPEC_NOT_FOUND` even though the document content is valid. | M013 remote-spec proof scripting |
| 20 | CLI/report status regressions can hide if `resolveReportStatus()` inspects normalized governance shapes before normalization runs. | The summary/report status code executes on raw `GovernanceFailure` objects, where the severity discriminator is `failureClass`; checking a later serialized `class` field leaves semantic failures invisible and can keep status `ok`. | When touching report-status selection, read `GovernanceFailure.failureClass` directly in pre-normalized code paths and only rely on serialized `class` after report normalization. | M013 remote-spec provenance reporting |
| 21 | Fully covered HTTP payload scenarios with semantic drift now keep coverage dimensions green while the overall CLI/report status stays `partial`. | Payload semantics are published additively: `coverage.operations/status/parameters/aggregate` can remain `COVERED` at 100%, but fail-closed governance diagnostics still downgrade the top-level report status and CLI summary status. | When updating HTTP CLI/report tests around semantic payload failures, assert `- status: partial` / `report.status === "partial"` together with unchanged covered coverage dimensions instead of expecting the old all-green `ok` status. | M013 static HTML report closeout |
| 22 | CI delivery surfaces will silently understate supported report UX if success bundles don't fail when a required HTML sibling is missing. | Once Yanote's supported operator surface includes `yanote-report.html` / `yanote-async-report.html`, letting collectors export only JSON on the happy path makes CI bundles and docs look green while dropping part of the supported contract. | Make success-path collectors/exporters assert required HTML siblings explicitly and keep failure bundles truthful by only omitting HTML when the analyzer never produced it. | M013 CI artifact retention |
| 23 | Public boundary verifiers need exact wording for local-first remote-opt-in support or docs will drift back toward implied combined/dashboard promises. | The same support boundary is repeated across README, docs landings, guides, branch-protection notes, and release/support docs; without literal verifier needles, future edits can easily reintroduce vague wording that overstates remote or combined-report support. | Keep shell doc verifiers pinned to the literal local-file/directory baseline, narrow remote single-document `http(s)` path, separate HTTP/async JSON+HTML artifact families, and explicit no-dashboard/no-combined boundary. | M013 delivery/support docs |
| 24 | Focused retained-proof verifiers that pin an exact bundle layout must be widened when later slices intentionally add shared artifact siblings. | M013 S02’s deprecated-operations proof originally treated `yanote-report.json` as the only success artifact, so once S03 made `yanote-report.html` a required sibling the closeout verifier failed even though product behavior improved. | When a shared writer gains additive outputs, update older focused verifiers to assert the new sibling explicitly instead of treating it as unexpected bundle drift; otherwise milestone integration will flag a false regression. | M013 milestone closeout |
| 25 | AsyncAPI 3.0 operation traits cannot carry `reply`, even though the operation object itself can. | The parser/schema merges `correlationId` from message traits into resolved messages, but `components.operationTraits.*.reply` is schema-invalid in `@asyncapi/parser`, so "trait-applied reply" proofs must keep `reply` inline and vary only the trait-supported message fields. | When proving inline-vs-trait parity for richer async semantics, use parser-merged message traits as the authoritative source for `correlationId`, retain `reply` from the operation object, and avoid inventing a custom trait merge layer. | M014 AsyncAPI trait semantics |
| 26 | Async declared semantics are not available from `AsyncCoverageResult` alone. | Coverage preserves routing, schema, and numerator truth, but the retained `declaredCorrelationId` / `declaredReply` metadata still lives on `operationContractsByKey`, so report/CLI surfaces cannot reconstruct the richer declaration section from coverage arrays after the fact. | When widening async JSON/HTML/CLI output with declared semantics, thread `operationContractsByKey` (or the canonical bundle) into the formatter layer and keep coverage math separate. | M014 async report contract wiring |
| 27 | Direct CLI probes in this repo should use the built `dist/yanote.cjs` entrypoint, not `npm exec tsx src/cli.ts ...`. | `yanote-js` does not declare `tsx`, so worktree-local direct probes that assume a TS runner fail before the CLI writes artifacts even though the built binary works. | For ad hoc CLI verification here, run `npm -C yanote-js run build` and then invoke `node yanote-js/dist/yanote.cjs ...` when you need the real command surface outside Vitest. | M014 CLI verification |
| 28 | AsyncAPI parser-backed malformed declaration coverage splits across two boundaries: schema-invalid shells fail before normalization, while runtime expressions like `$message.header#` survive and must fail closed inside the extractor. | `@asyncapi/parser` rejects non-object `correlationId`, missing `reply.address.location`, and other schema-invalid shapes before `loadAsyncApiSemanticsBundle()` builds a document, but it still passes parser-normalized declarations whose runtime-expression path is blank after `#`. | For M014 extraction tests, cover parser-surviving malformed cases with real fixtures and use direct `buildAsyncApiSemantics()` tests when you need to assert fail-closed handling for raw malformed shells the parser itself would reject. | M014 AsyncAPI extraction |
| 29 | Malformed async header fixtures need direct evaluator tests because the JSONL reader normalizes invalid header entries away before coverage code sees them. | `readAsyncEventsJsonl()` accepts only `{ state, value | reason }` header evidence objects; raw-string maps like `{ "reply_to": "orders.reply" }` are dropped during normalization and would otherwise look like ordinary missing-header evidence. | When you need to prove fail-closed handling for malformed async header evidence, add a direct `computeAsyncSemanticConformance()` / `computeAsyncCoverage()` test with a cast event object instead of relying on JSONL fixtures alone. | M014 async runtime-semantics testing |
| 30 | Async CLI success fixtures that exercise header-backed runtime semantics must use normalized `AsyncHeaderEvidence` objects, not raw string header values. | Once `async-report` gates on `runtimeSemantics`, JSONL headers like `{ "correlation_id": "corr-123" }` normalize away and the CLI exits with semantic runtime failures even though the declaration-only path used to pass. | For CLI/report/remote-spec proofs of satisfied correlationId or `reply.address`, keep fixture headers in `{ state: "captured", value: "..." }` form; reserve raw-string header shapes for direct malformed-evidence tests outside JSONL normalization. | M014 async CLI runtime proofs |
| 31 | `ASYNC_SEMANTIC_SPEC_INVALID` can stop `yanote async-report` before `yanote-async-report.json` is written, while supported-shape runtime failures still emit a partial report artifact. | Malformed declaration shells fail during AsyncAPI semantic extraction, before the report writer runs, but unsupported/missing/unavailable/mismatched runtime proof outcomes happen after report construction. | In closeout verifiers and UAT, assert stderr + exit code for malformed-spec cases and only expect `yanote-async-report.json` when extraction succeeded far enough to build report data. | M014 async CLI invalid-spec handling |
| 32 | When an extractor helper returns additive metadata plus the main contract payload, a later object spread can silently erase previously merged top-level arrays. | `ResolvedKafkaMessageContracts` started carrying `bindingSupport`, and spreading `...messageContract` after the already-merged channel/operation/message rows replaced the full merged array with the message-only subset. | In `yanote-js/src/spec/asyncapi.ts`, destructure helper-only metadata like `bindingSupport` before spreading the rest of the resolved message contract into `KafkaOperationContract`. | M014 async binding extraction |
| 33 | The M014 S03 Kafka-binding CLI proof is expected to stay `status: partial` under `--profile local` while still generating the required JSON/HTML artifacts and `binding_*` machine tokens. | The fixture intentionally leaves `users.lifecycle` uncovered so the binding matrix shows supported vs declared-only vs deferred rows without pretending all async operations are proven, and the local profile surfaces that as a warning rather than a hard failure. | For binding-matrix verification and future closeout/UAT, assert artifact generation plus `Kafka Binding Support` / `bindingSupport` / `binding_*` truth instead of expecting an all-green `status: ok`. | M014 async binding verification |
| 34 | Milestone closeout in this repo may need `M###-VALIDATION.md` as the structured success-criteria checklist even when `M###-ROADMAP.md` renders only the slice overview table. | During M014 closeout, the roadmap file exposed the milestone vision and slice overview, but the explicit pass/fail checklist and cross-slice audit lived in `M014-VALIDATION.md`. | For future milestone completion, verify code changes and slice artifacts first, then use the validation document plus slice summaries as the canonical closeout audit before calling `gsd_complete_milestone`. | GSD milestone closeout |
